# GET-запросы. Нормализация данных и прелоадер

Всё так! Обращаясь к файлу `data.js`, мы получали данные, при необходимости фильтровали их, передавая дальше компонентам для отображения. Но в веб-разработке базы данных и серверы не просто так выделены в отдельное направление, известное как **backend**. 

Разделение обязанностей помогает создавать крутые и сбалансированные проекты: клиентское приложение отвечает за работу с интерфейсом, база данных управляет информацией веб-приложения, а серверы выступают в роли посредников между клиентом и базой данных, проводя дополнительные операции с ними.

## `GET`-запросы

**`GET`-запросы** — это способ получения данных с сервера. Они выполняются через `URL`. Все запросы разные и предоставляют разную информацию. Обращаясь к API, мы используем **эндпоинты** (маршруты запроса). Эндпоинты определяют, какие именно данные необходимо получить, аналогично **роутам** на клиентской стороне веб-приложения.

### Работа с эндпоинтами

Для работы с эндпоинтами нужно создать:

- папку `api` внутри основной директории `app`
- новый файл `config.js` в папке `api`
- объект `endpoints` в файле `config.js`:

```javascript
export const BASE_URL = 'https://api-code-2.practicum-team.ru';

export const endpoints = {
  games: `${BASE_URL}/games`,
};
```

В коде выше мы создаём константу `BASE_URL`, представляющую базовый адрес API. В объекте `endpoints` у нас пока только один маршрут — `/games`, который использует базовый путь. Хотя это может показаться сложным, поверь, это очень удобно. Нам не нужно повторять длинную строку в каждом `GET`-запросе.

Посмотри на полный путь эндпоинта для получения данных игр 👇🏻

```
https://api-code-2.practicum-team.ru/games
```

По этому эндпоинту можно получить данные всех игр, а внутри веб-приложения заниматься обработкой и фильтрацией этих данных. Открой этот адрес в браузере, посмотри, что там. 

Когда игр немного, Pindie легко с этим справиться. Но что, если количество игр увеличится в тысячу раз? Получается, что, кроме основных задач по сборке и рендерингу компонентов, придётся разом получать данные всех игр, а затем проводить сложные операции, замедляя работу всего веб-приложения.

### Кусочки данных

Фильтрацию данных лучше всего выполняют сами базы данных, которые созданы и оптимизированы специально для подобной работы. Кроме фильтрации, они проводят и сортировку, и упорядочивание гораздо быстрее, чем веб-приложение.

Поэтому лучшим решением будет частичное получение данных. При запросе только нужной информации уменьшается объём передаваемых данных и увеличивается скорость работы веб-приложения. Например, мы можем запросить все игры в определённой категории или только одну игру, сокращая ненужную нагрузку на API.

Эндпоинты позволяют получить только нужный **кусочек данных**. При обращении к эндпоинту `/games/1` мы получаем данные первой игры в базе данных, а эндпоинт `/games/categories.name=pixel` возвращает отсортированные игры из категории `Пиксельные`

Все API разные и предоставляют разные эндпоинты для получения данных. У качественного и проверенного API обычно есть документация, в которую обязательно нужно заглянуть, чтобы узнать, к какому эндпоинту обращаться за нужными данными.

### Получение данных по ID

Для получения данных конкретной игры по её идентификатору мы можем воспользоваться `GET`-запросом к соответствующему эндпоинту. 

В API веб-приложения Pindie для этого есть маршрут `/games/${id}` , где `${id}` — это уникальный `ID` запрашиваемой игры.

В прошлом уроке мы создали функцию `getData` для получения данных из API. Она принимает в себя `URL` и выступает в роли универсального шаблона для получения данных из любого источника. Новая функция `getGameDataById` использует её внутри себя 👇🏻

```javascript
export const getGameDataById = async (url, id) => {
  const data = await getData(`${url}/${id}`);
  return data;
};
```

Здесь функция принимает `URL` и идентификатор игры, которые составляют `GET`-запрос `${url}/${id}`. Затем она отправляет запрос по указанному маршруту, получая только данные о конкретной игре. Такой подход особенно полезен, когда на детальной странице игры нам нужна лишь информация о выбранной игре, а не весь список игр.

### Получение данных по категориям

В API веб-приложения Pindie есть ещё один полезный маршрут для получения игр, отсортированных по разным категориям `/games/categories.name=${category}`. ****Здесь `${category}` ****— это название категории игр.

Вот так будет выглядеть новая функция `getGamesDataByCategory` 👇🏻

```javascript
export const getGamesDataByCategory = async (url, category) => {
  const data = await getData(`${url}?categories.name=${category}`);
  return data;
};
```

Выше функция принимает URL и категорию, после чего отправляет `GET`-запрос с указанными параметрами. На этот раз полученные данные представляют собой массив игр, так как выбранная категория может содержать не только одну, а сразу несколько игр.

{video:https://code.s3.yandex.net/kids-web/vids/getCategory.mp4|controls:true|autoplay:0|pip:false|controlsList:nodownload}

Новая функция облегчает работу веб-приложения, позволяя проводить фильтрацию на стороне API, а не на стороне клиента. Во всех роутах для категорий игр (`/new`, `/popular`, `/shooters` и других) мы можем использовать эту функцию для получения данных об играх каждой категории.

Чтобы загрузка данных была ещё быстрее, стоит отправлять серверные `GET`-запросы, делая страницы категорий (роуты) серверными компонентами. Важно помнить про использование ключевого слова `async`, чтобы наши компоненты, как и функции получения данных, работали асинхронно.

## Нормализация данных

API создаются разными веб-разработчиками и даже большими командами, которые работают над улучшениями и регулярно выпускают обновления. Работая с внешними API, мы не можем предсказать изменения, которые внесут разработчики. Проблема в том, что сегодня возвращаемый ключ может называться, к примеру, `title`, а завтра, после выхода новой версии API, этот же параметр изменится на `name`. После таких непредвиденных изменений в нашем веб-приложении могут появиться ошибки и оно перестанет корректно работать. 

Чтобы справиться с этой проблемой и так сильно не зависеть от структуры данных конкретного API, применяется **нормализация данных**. Это процесс приведения данных к общему виду перед тем, как мы начнём с ними взаимодействовать.

В API веб-приложения Pindie недавно как раз произошли изменения. В объектах каждой игры ключ `category` превратился в `categories`, а `users` вообще во что-то непонятное. Такие нововведения могут поставить под угрозу работоспособность наших компонентов, и есть два способа решить эту проблему: 

1. Переписать код всех компонентов, которые работают с этими ключами, чтобы они могли обрабатывать их новые имена. Но это потребует значительного времени и усилий.
2. Нормализовать данные, создав функцию, которая будет обрабатывать получаемую информацию перед тем, как она перейдёт дальше в компоненты.

Второй вариант гораздо эффективнее, поэтому создадим функцию нормализации данных.

### Нормализация объектов

![](https://pictures.s3.yandex.net:443/resources/Frame_1546_2_1708950741.png)

```javascript
const normalizeDataObject = (obj) => {
  return {
    ...obj,
    category: obj.categories,
    users: obj.users_permissions_users,
  };
};
```

Эта функция как переводчик для наших данных принимает информацию об игре в виде объекта и создаёт новый объект, проводя необходимые изменения.

Внутри функции мы используем оператор `spread` (конструкция `…obj`). Он выполняет распаковку объекта, создавая копию всех его ключей и значений в новом объекте функции, избегая ручного переписывания каждого поля.

Далее мы создаём новые ключи в этом объекте:

- Ключ `category` принимает значение ключа `categories`. Таким образом, мы сохраняем значение из старого ключа в новом, переименовывая его.
- Аналогично ключ `users` принимает значение ключа `users_permissions_users`

Таким образом, функция `normalizeDataObject` помогает адаптировать данные, полученные с сервера, чтобы мы могли не вносить изменения в каждый компонент, сохраняя внутри прежние названия ключей. В случае изменений в API достаточно внутри этой функции обновить только изменённый ключ на тот, который мы хотим использовать.

Конечно!

### Нормализация массивов

Для нормализации массива создадим функцию `normalizeData`, которая принимает массив объектов и возвращает новый массив, в котором каждый объект нормализован с использованием ранее созданной функции `normalizeDataObject` 👇🏻

```javascript
export const normalizeData = (data) => {
  return data.map((item) => {
    return normalizeDataObject(item)
  })
}
```

Аски, ты прав, поэтому давай улучшим наши функции, которые отправляют `GET`-запросы к API, чтобы они возвращали нормализованные данные, готовые для использования внутри компонентов и маршрутов по категориям игр.

### Модифицируем функции

В функциях ниже перед возвратом данных мы применяем функции нормализации. Для игр по категориям используем функцию `normalizeData` для работы с массивом, а для каждой отдельной игры — функцию `normalizeDataObject` для работы с объектом 👇🏻

```javascript
export const getGamesDataByCategory = async (url, category) => {
  const data = await getData(`${url}?categories.name=${category}`);
// Применяем функцию нормализации для работы с массивом
  return normalizeData(data);
};

export const getGameDataById = async (url, id) => {
  const data = await getData(`${url}/${id}`);
// Применяем функцию нормализации для работы с объектом
  return normalizeDataObject(data);
};
```

# Работа над Pindie

Поместим четыре новые функции в файл `api-utils.js`

Показываем, как вывести нормализованные данные игр по категории `popular`, используя функцию отправки `GET`-запроса `getNormalizedGamesDataByCategory` 👇🏻

{video:https://code.s3.yandex.net/kids-web/vids/vision.mp4|controls:true|autoplay:0|pip:false|controlsList:nodownload}

Страница категории — компонент серверный, а значит, для правильного запроса нужно использовать `async/await` (повторить механику работы этих команд можно в уроке «Опять `fetch`. Синтаксис `async/await`»).

Теперь применим функцию `getNormalizedGameDataById` на отдельной странице игры. 

Обрати внимание на строку `"use client"` — компонент клиентский, а значит, `GET`-запрос нужно выполнять в хуке `useEffect` 👇🏻

```javascript
useEffect(() => {
	async function fetchData() {
		const game = await getNormalizedGameDataById(endpoints.games, props.params.id);
		game.error ? setGame(null) : setGame(game);
	}
	// Вызываем функцию при первом отображении компонента
	fetchData();
}, [])
```

Внутри хука мы создаём асинхронную функцию `fetchData` и используем ключевое слово `await` перед `GET`-запросом. Это гарантирует, что код ниже запроса выполнится только после того, как операция завершится. При отправке запроса данным нужно пройти путь от браузера до API и обратно, а это занимает какое-то время. Если просто вызвать `getNormalizedGameDataById`, хук не будет ждать её завершения и начнёт выполнять код дальше, что может повлечь за собой ошибки.

В сам запрос передаём обязательные параметры:

- `URL` (другими словами, путь запроса) из объекта `endpoints`. В нём у нас пока один маршрут — `games`, поэтому используем его.
- `ID` — уникальный идентификатор игры. Его мы получаем из параметров `props` при роутинге, когда кликаем на карточку желаемой игры.

Для хранения результата запроса мы создаём переменную `game`. Она принимает в себя объект с данными игры. Если данные получены, функция `setGame` меняет состояние, отображая на странице игру и информацию о ней. В противном случае мы видим сообщение `Такой игры не существует :(`

## Побочный эффект интерфейса

Пришло время проверить работу новых функций в нашем проекте 👇🏻

{video:https://code.s3.yandex.net/kids-web/vids/interfaceBug.mp4|controls:true|autoplay:0|pip:false|controlsList:nodownload}

При переходе на детальную страницу игры можно заметить **мерцание контента**. Когда мы делаем асинхронный `GET`-запрос к API, компонент продолжает свою отрисовку, не дожидаясь выполнения функции. Поэтому при первом рендеринге мы видим сообщение об отсутствии данных, и только затем, когда данные приходят, компонент обновляется и отображает игру на странице, вызывая повторный рендеринг.

Компоненту `<GamePage/>` нужно динамически обновлять данные игр, а в будущем в нём будет реализован механизм голосования. Серверные компоненты не способны справиться с этими задачами, потому что они получают данные на сервере до отправки результата на сторону клиента.

Проблему видимого мерцания в клиентских компонентах решает **прелоадер** — временный элемент, появляющийся во время загрузки данных. Это может быть анимированный индикатор загрузки или обычный текст, уведомляющий пользователя о том, что что-то загружается. В серверных компонентах такой проблемы нет из-за их статичного характера.

### Работа с прелоадером

Готовый прелоадер можно найти в [репозитории](https://github.com/Yandex-Practicum/pindie-prebuild-components){target="_blank"}. Перенесём папку с файлами компонента `Preloader` в папку `app/components` нашего проекта.

Затем на странице `GamePage` нужно определить момент, когда следует отображать новый компонент, а когда его нужно скрыть. Для этого потребуется создать дополнительное состояние прелоадера, используя хук `useState` 👇🏻

```javascript
const [preloaderVisible, setPreloaderVisible] = useState(true);
```

При переходе на страницу и загрузке данных нужно отображать прелоадер, поэтому состояние компонента по умолчанию принимает значение `true`

После получения данных игры можно скрыть прелоадер, используя функцию `setPreloaderVisible` внутри хука `useEffect` 👇🏻

```javascript
useEffect(() => {
	async function fetchData() {
		const game = await getNormalizedGameDataById(endpoints.games, props.params.id);
		setPreloaderVisible(false);
	}
	fetchData()
}, [])
```

Осталось доработать условный рендеринг, добавив ещё одно условие 👇🏻

```javascript
<main className="main">
	{game ? (
		// Разметка игры
	) : preloaderVisible ? (
		<Preloader />
	) : (
		<GameNotFound />
	)}
</main>
```

Выше мы проверяем текущее состояние игры. Если данные получены, отображаем их на странице. Дополнительно мы проверяем состояние прелоадера. Если оно равно `true`, отображаем прелоадер на странице. В случае возникновения ошибки, когда данные об игре не могут быть получены по какой-то причине, мы выводим компонент `<GameNotFound />`.

Рассказываем.

### Обработка ошибок

В уроке **«**[Опять fetch.  Синтаксис async/await](https://practicum.yandex.ru/trainer/kids-web/lesson/4485f88d-a756-44eb-929f-c7cd6a8a5811/){target="_blank"}**»** мы создали функцию `isResponseOk`, которая проверяет запрос к API на наличие ошибок. Если в функции есть ошибки, она возвращает `false`, если нет — `true`

Используя тернарный оператор и новую функцию внутри хука `useEffect`, проверим получение данных игры на наличие ошибок 👇🏻

```javascript
useEffect(() => {
	async function fetchData() {
		const game = await getNormalizedGameDataById(endpoints.games, props.params.id);
		isResponseOk(game) ? setGame(game) : setGame(null);
		setPreloaderVisible(false);
	}
	fetchData()
}, [])
```

Обращаясь к функции, мы передаём результат выполнения `GET`-запроса. Если ошибок не найдено, устанавливаем объект игры в состояние `game`. Иначе говоря, сбрасываем состояние, тем самым провоцируя отображение компонента `<GameNotFound />`

Но одной проверки внутри хука недостаточно. Чтобы понимать, действительно ли произошла ошибка, стоит доработать функции получения данных из API 👇🏻

```javascript
export const getNormalizedGamesDataByCategory = async (url, category) => {
	const data = await getData(`${url}?categories.name=${category}`);
	return isResponseOk(data) ? normalizeData(data) : data;
};

export const getNormalizedGameDataById = async (url, id) => {
  const data = await getData(`${url}/${id}`);
  return isResponseOk(data) ? normalizeDataObject(data) : data;
};
```

Выше в случае отсутствия ошибок мы передаём данные функциям нормализации. В случае обнаружения ошибок возвращаем их без дополнительной обработки.
