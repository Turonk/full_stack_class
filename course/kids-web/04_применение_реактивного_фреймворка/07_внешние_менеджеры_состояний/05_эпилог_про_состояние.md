# Эпилог про состояние

Всё так. И главная трудность заключается в том, что существует множество способов работы с состоянием — среди них нет единственно верного. В зависимости от того, что является источником, сколько компонентов использует одно состояние и как именно оно это делает, разработчик должен уметь выбрать определённый способ работы с ним.

![](https://pictures.s3.yandex.net:443/resources/IMG_4728_1709559922.jpg)

Начнём с того, что вне веб-приложения состояние хранится в двух источниках: на бэкенде и в хранилище браузера. Они подходят для разных целей, давай ещё раз это сформулируем. 

## Бэкенд

**Бэкенд** — это долговременное хранилище состояния. В проекте Pindie практически всё состояние приложения изначально берётся из бэкенда. Когда мы впервые заходим на сайт, вызываем `checkAuth()`, чтобы узнать у бэкенда, авторизован ли пользователь. Если на странице есть список карточек с играми, то так же сначала выполняем запрос к хранилищу, чтобы получить данные для отрисовки списка карточек. Наконец, если мы заходим на страницу конкретной игры, вновь обращаемся к бэкенду, чтобы получить расширенный набор данных для отдельно взятой игры.

Данные для карточек с играми и для страницы одной игры — это статичные данные, пользователь не может сам удалить или добавить игру в Pindie. Но он может проголосовать за игру — таким образом, число голосов на странице игры изменится. Когда человек отдаёт свой голос за игру, мы первым делом выполняем запрос к бэкенду и только после его успешного выполнения рисуем новое количество голосов на странице игры. Чекай, как это выглядит 👇🏻

```javascript
const handleVote = async () => {
    const jwt = authContext.token
    let usersIdArray = game.users.length
      ? game.users.map((user) => user.id)
      : [];
    usersIdArray.push(authContext.user.id);
    // Сначала выполнили запрос на добавление голоса
    const response = await vote(
      `${endpoints.games}/${game.id}`,
      jwt,
      usersIdArray
    );
    // Только если запрос успешный,
    if (isResponseOk(response)) {
      // отображаем новое количество голосов
      setGame(() => {
        return {
          ...game,
          users: [...game.users, authContext.user],
        };
      });
      setIsVoted(true);
    }
  };
```

Запрос на бэкенд позволяет сохранить новое количество голосов за игру. Когда пользователь перезагрузит страницу, на ней всё так же будет актуальное количество голосов.

## Хранилище браузера

В уроке «Запросы с `JWT`-токеном и его хранение» мы познакомили тебя с `localStorage` — внутренним хранилищем браузера. Оно так же, как и бэкенд, является долговременным. 

В Pindie мы используем его в механизме авторизации: после входа в профиль сохраняем токен от бэкенда во внутреннее хранилище. Когда пользователь перезагрузит страницу, токен всё ещё будет лежать в `localStorage`. Благодаря этому, Pindie незаметно для пользователя с помощью функции `checkAuth()` проверяет, авторизован ли он, выполнив запрос к бэкенду с токеном из `localStorage`

## Локальное состояние компонента

Верно! **Локальное** означает, что оно доступно только в том компоненте, который его создал, и тем, кому это состояние было явно передано через `props`. Как правило, с помощью `useState` создаётся очень маленькое состояние, простые строковые числовые переменные или флаги со значением `true`/`false`. Такие переменные состояния почти всегда изолированы в компоненте и имеют единственную узкую задачу.

В Pindie используется хук `useState` в основном для создания переменных состояния с узкой задачей: 

1. В компоненте `Header` задаём переменную состояния `popupIsOpened`, а в зависимости от её значения показываем или не показываем всплывающее окно с авторизацией.
2. В компоненте `Promo` есть переменная `codeIsVisible`, по которой определяем, отобразить или скрыть промокод.
3. Ещё один яркий пример — кастомный хук `useGetDataByCategory`. В нём создаём состояние, в котором храним не просто строку, число или `true`/`false`, а целый объект — данные об играх. Несмотря на это, переменная состояния `data`, которая создаётся в этом же хуке, не передаётся через пропсы только в компонент `CardList`. То есть `data` сохраняет свойство простоты, так как используется только для того, чтобы отрисовать конкретный список карточек.

## Глобальное состояние

Кроме локального состояния, бывает ещё и **глобальное состояние** — мы начали говорить о нём в уроке «Глобальное состояние. Идея». Глобальное — это такое состояние, которое доступно везде, в любом компоненте приложения, для реализации которого существует множество вариантов.

### Props-drilling

В уроке «Глобальное состояние. Идея» мы подготовили методы работы с ним. Там же создали компонент `App` , в котором при помощи `useState` сделали несколько переменных состояния.

Заметь, что `App` был вызван в самом верху иерархии компонентов, то есть в `RootLayout`. Такой подход позволил бы нам передать через `props` все переменные состояния из `App` в дочерние компоненты, вплоть до самого нижнего в иерархии. Но мы не стали так делать из-за проблем, которые возникают при пропс-дриллинге:

1. Все компоненты знают обо всех переменных состояния. Так как мы прокидываем состояние сверху вниз, каким-то компонентам посередине пути часть состояния может быть вообще не нужна. Это увеличивает связность компонентов.
2. Название React, как можно догадаться, дано не случайно: если меняется состояние, происходит моментальная **реакция** и перерисовка тех компонентов, которые непосредственно зависят от изменённого состояния. Отсюда и проблема выше: если поменять значение одной из переменных состояния, которое мы через `props` передали из `App`, React перерисует все компоненты, которые получили эту переменную состояния, даже если компонент никак её не использует, а просто передаёт ниже.

### Context

В уроке «Встроенное решение — React Context» мы рассмотрели инструмент, который позволяет работать с глобальным состоянием без тех проблем, которые возникают у метода пропс-дриллинга. Благодаря `context` не нужно передавать состояние через `props`

Главный недостаток этого метода — проблема лишних перерисовок, а также сложность работы с большим количеством стейтов или большим количеством контекстов.

Если много контекстов, то любой компонент, в котором нам понадобится состояние, необходимо обернуть в `Provider`, — получится много обёрток. А если в приложении много состояний, придётся пробрасывать в контекст огромные объекты. С таким кодом действительно неудобно работать 🫠

### Библиотеки для управления состоянием

Во фронтенд-разработке есть отдельные библиотеки, которые позволяют решить проблемы из подходов выше.

Мы в Pindie используем Zustand (рассказывали в прошлом уроке). Несмотря на то что таких библиотек сотни и они во многом различаются, у них есть общее — они позволяют отделить работу с данными, которые отображает приложение, от способа их отображения. Иными словами, они позволяют отделить данные от React-компонентов. 

В Pindie при помощи Zustand мы создаём хранилище состояния, которое лежит в отдельном файле `app/store/store.js`. Любой компонент в Pindie может импортировать хук `useStore` и получить доступ к тем данным состояния, которые нужны именно этому компоненту.

## Эпилог эпилога

Ещё раз подчеркнём, что задача проектирования состояния очень сложна и многогранна. Разработчики сталкиваются с ней с самых ранних этапов создания практически любого приложения. 

Перед тем как приступать к написанию кода, обязательно нужно ответить на вопросы: с какими данными будет работать приложение, какие из них будут видны пользователю в интерфейсе, как часто они будут обновляться, что вообще пользователь может делать в приложении. Вопросов на самом деле больше, и они разнятся от приложения к приложению.
