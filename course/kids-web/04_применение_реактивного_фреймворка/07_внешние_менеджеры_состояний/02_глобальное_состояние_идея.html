Глобальное состояние. Идея

Да! Удобно управлять состоянием позволяет, как ясно из названия, хук `useState`

Посмотрим на его работу ещё раз:

const [state, setState] = useState(initialState)

Переменная `state` — это состояние, которое может принимать любые формы данных: от строк, чисел и логических значений до объектов и целых массивов. Функция `setState` — своего рода переключатель состояния, который меняет его, когда нам это нужно. Несмотря на мощь этого хука, каждый компонент всё равно хранит своё состояние только внутри себя.

![](https://pictures.s3.yandex.net:443/resources/IMG_4711_2_1709305201.jpg)

Локальное состояние

Состояние, которое хранится, обновляется и используется компонентом внутри себя, называется **локальным состоянием**. Это удобный механизм, который скрывает состояние от других компонентов, делая его уникальным.

Представь: на странице несколько кнопок, каждая из которых занята своим делом. Первая кнопка позволяет поставить лайк, вторая — добавить товар в корзину, а третья — проголосовать. Кликая на каждую из них, мы хотим, чтобы они выполняли свою роль и не вмешивались в работу других кнопок.

{video:https://code.s3.yandex.net/kids-web/vids/Видео_без_названия__сделано_в_Clipchamp.mp4}

Использовать локальное состояние будет отличным решением. Это позволит управлять поведением каждого компонента отдельно от других элементов веб-приложения.

Ещё один плюс использования локального состояния — его способность изолировать данные. Представь блок с отзывами, в которых пользователи оценивают и комментируют разный контент. Каждая карточка отзыва хранит рейтинг и комментарий только одного пользователя в локальном состоянии, не вмешиваясь в другие данные. Такой подход обеспечивает надёжную изоляцию, предотвращая нежелательные воздействия на остальные элементы интерфейса.

Глобальное состояние: определение и источники

Иногда возникают ситуации, когда какие-то данные важны для нескольких компонентов одновременно. В подобных случаях можно воспользоваться общим хранилищем. Такое хранилище называют **глобальным состоянием**.

Всё верно! Информация, хранящаяся в глобальном состоянии, доступна каждому компоненту в любой момент времени.

В прошлой теме, создавая механизм авторизации пользователя, мы познакомились с этой концепцией. Тогда `JWT`-токен пользователя записывался в память браузера, благодаря чему другие компоненты могли определить, авторизован пользователь или нет, изменяя своё поведение.

Но не только браузер может сохранять и получать данные, которые будут общими для всех компонентов. Источником глобального состояния может быть **память браузера** — к ней есть доступ у всех компонентов после монтирования.

Ещё один способ — запросы к API. Отправляя запросы на сервер, можно регулярно обновлять данные веб-приложения.

{quiz-task} background: | #f1f1ef content: | ❗ Состояние данных на сервере — тоже глобальное состояние. Запросы для получения этих состояний может делать любой компонент. {/quiz-task}

Давай!

Проблема заключается в том, что страницы категорий игр — компоненты серверные. Это значит, что при первом запуске Pindie браузер получает страницы категорий игр с уже готовыми данными, которые больше не обновляются. Это приводит к тому, что после того как пользователь проголосует за игру на её детальной странице, количество голосов обновится только на ней. Новое число голосов не отобразится в карточке игры на странице её категории или на главной странице 👇🏻

{video:https://code.s3.yandex.net/kids-web/vids/RouteProblem.mp4}

Для решения этой проблемы нужно превратить все роуты категорий игр в клиентские компоненты и изменить функцию получения данных.

Запрос для получения этих данных в клиентских компонентах можно делать каждый раз во время монтирования, а не только при первой сборке. Ты уже умеешь указывать тип компонента, добавляя строку `use client`. А получать данные в клиентском компоненте позволяет хук `useEffect` совместно с хуком `useState` для передачи данных в дочерний компонент `CardsList`

Компонентов категорий много, а новый механизм получения данных один. Чтобы избежать дублирования кода, вместо обычной функции **создай собственный хук** (ниже — инструкция). Если потребуется внести изменения, достаточно сделать это внутри хука, не переписывая код каждого роута.

**Шаг 1. Создание файла и импорт кода**

Создай файл `api-hooks.js` в папке `app/api` и импортируй хуки `useState`, `useEffect`, а также функцию получения нормализованных данных игр — `getNormalizedGamesDataByCategory` 👇🏻

import {useState, useEffect} from 'react';
import {getNormalizedGamesDataByCategory} from './api-utils';

**Шаг 2. Параметры**

Все хуки начинаются со слова `use`, и наш кастомный хук не исключение.

Пусть в качестве параметров он будет принимать эндпоинт API и название категории игр 👇🏻

export const useGetDataByCategory = (endpoint, category) => {
};

**Шаг 3. Переменная `data`**

Используя хук `useState`, создай переменную `data`, которая будет принимать в себя массив с данными игр.

По умолчанию массив игр пуст, а значит, принимает значение `null` 👇🏻

export const useGetDataByCategory = (endpoint, category) => {
	const [data, setData] = useState(null);
};

**Шаг 4. Получение данных**

Хуком `useEffect` настрой получение данных игр при монтировании компонента, в котором будет использоваться хук 👇🏻

export const useGetDataByCategory = (endpoint, category) => {
	const [data, setData] = useState(null);
	useEffect(() => {
		// Здесь будет получение данных
  }, []);
};

**Шаг 5. Функция `fetchData`**

Создай асинхронную функцию `fetchData` для получения данных игр.

Внутри неё ты будешь использовать подготовленную функцию `getNormalizedGamesDataByCategory` и после получения данных игр установишь их в переменную `data`, используя функцию `setData`

Чтобы функция запустилась при монтировании компонента, не забудь её вызвать 👇🏻

export const useGetDataByCategory = (endpoint, category) => {
	const [data, setData] = useState(null);
	useEffect(() => {
		async function fetchData() {
      const data = await getNormalizedGamesDataByCategory(endpoint, category);
      setData(data);
    }
		fetchData();
  }, []);
};

**Шаг 6. Возвращение данных**

Наш кастомный хук можно считать отдельной функцией, в которой мы получаем данные игр по заданной категории.

Важно, чтобы хук возвращал полученные данные в компонент страницы категории, поэтому добавь последний штрих — `return`👇🏻

export const useGetDataByCategory = (endpoint, category) => {
  const [data, setData] = useState(null);
  useEffect(() => {
    async function fetchData() {
      const data = await getNormalizedGamesDataByCategory(endpoint, category);
      setData(data);
    }
    fetchData();
  }, []);
  return data;
};

**Шаг 7. Применение хука**

Пришло время применить новый хук на примере роута категории новых игр. Не забывай сделать компонент `New` клиентским. А затем импортируй созданный хук 👇🏻

'use client';
import { useGetDataByCategory } from "./api/api-hooks";
// ...другие импорты

Кроме хука, в компонент должен быть импортирован объект `endpoints` из файла `config.js`, а также компонент `CardsList`

**Шаг 8. Переменная `newGames`**

Для хранения данных, которые будешь получать из хука, создай внутри компонента `New` переменную `newGames`

Первым параметром хука передай эндпоинт API, а вторым параметром — название самой категории 👇🏻

export default function New() {
  const newGames = useGetDataByCategory(endpoints.games, "new");
  return (
		// ...Разметка компонента
  );
}

Супер! Теперь при монтировании компонента хук будет получать данные игр и сохранять их в переменную `newGames`

**Шаг 9. Компонента `CardsList`**

Затем нужно передать переменную в качестве значения параметра `data` компонента `CardsList`👇🏻

export default function New() {
  const newGames = useGetDataByCategory(endpoints.games, "new");
  return (
		<main className="main-inner">
			<CardsList id="new" title="Новые" data={newGames} />
		</main>
  );
}

Ура! Теперь роут категории новых игр будет получать актуальные данные игр при каждом монтировании.

**Шаг 10. Обработка ошибок**

Осталось только обработать ошибки, если они возникнут при получении данных.

Для этого импортируй знакомый нам компонент `Preloader`👇🏻

import { Preloader } from "./components/Preloader/Preloader";

**Шаг 11. Финальные штрихи**

В уроке «Условный рендеринг» мы научились отображать разные части интерфейса. Поэтому проверь переменную `newGames` и, если она будет пустой, отобрази прелоадер, сигнализирующий пользователям о проходящей загрузке. Когда данные будут получены, на экране отобразится компонент `CardsList` с карточками игр 👇🏻

export default function New() {
  const newGames = useGetDataByCategory(endpoints.games, "new");
  return (
    <main className="main-inner">
      {newGames ? (
        <CardsList id="new" title="Новые" data={newGames} />
      ) : (
        <Preloader />
      )}
    </main>
  );
}

Поздравляем!

Используя новый хук, ты отправляешь запросы к API, тем самым взаимодействуя с глобальным состоянием, которое находится на сервере. Важно понимать, что каждый из способов работы с глобальным состоянием подходит для определённых задач. Веб-разработчики часто комбинируют их, балансируя работу веб-приложения.

{quiz-task} background: | #f1f1ef content: | ❗ Память браузера открыта пользователю, а значит, хранить секретные данные в ней небезопасно. Такую информацию можно хранить на сервере, но если её будет много, это плохо скажется на производительности, ведь придётся отправлять тонну запросов из каждого уголка веб-приложения. {/quiz-task}

Глобальное состояние внутри приложения

Веб-приложение похоже на множество коробок, которые лежат одна в другой. Каждый компонент может содержать много других компонентов внутри себя. Например, в компоненте `RootLayout` веб-приложения Pindie есть дочерний компонент страницы. По умолчанию это главная страница — компонент `HomePage`. В свою очередь `HomePage` — это родительский компонент для списка игр — компонента `CardsList`. А внутри самого `CardsList` находятся отдельные карточки игр — компоненты `Card`, которые также представляют его дочерние компоненты. Вложенность компонентов может быть очень большой, особенно в крупных проектах.

![](https://pictures.s3.yandex.net:443/resources/Frame_1559_1_1709306449.png)

Чтобы компоненты этого дерева могли обмениваться данными глобального состояния, используют хук `useState` в самом главном родительском компоненте `RootLayout`. Передачу данных можно реализовать при помощи параметров (`props`).

С параметрами мы уже давно знакомы благодаря уроку «Отсыпаем `props`ы», а передавать через них состояние в компоненты научил урок «Внутреннее состояние. Хук `useState`». Там речь шла про всплывающее окно с формой авторизации пользователя.

Родительский компонент `Header` передавал несколько параметров дочернему компоненту `Popup`, чтобы контролировать его поведение, открывая и закрывая окно в нужный момент.

![](https://pictures.s3.yandex.net:443/resources/Frame_1560_1709306548.png)

В случае с модальным окном состояние будет храниться внутри компонента шапки сайта, а получить к нему доступ смогут только его дочерние компоненты. Поэтому такое состояние нельзя назвать глобальным.

Основная идея глобального состояния в том, чтобы хранить все важные данные на **самом верхнем уровне** и передавать их вниз, позволяя дочерним компонентам удобно использовать эти данные и обрабатывать события.

В Pindie можно один раз проверить авторизацию пользователя на уровне корневого компонента `RootLayout`, а в дочерних компонентах уже не выполнять дополнительные запросы, что увеличит скорость работы веб-приложения и поможет избежать дублирования кода.

Как с этим работать

Допустим, мы уже используем `useState` в компоненте `RootLayout` и теперь нам нужно передать глобальное состояние самому младшему компоненту `Card`

Для этого придётся передавать их через все промежуточные компоненты, образуя цепочку параметров. Этот процесс называется **пропс-дриллингом** (с английского — «бурение»).

![](https://pictures.s3.yandex.net:443/resources/Frame_1561_2_1709306598.png)

Верно, но такой подход имеет свои недостатки:

- Во-первых, компонентам-посредникам (`HomePage` и `CardsList`) эти данные, возможно, вообще не нужны и мы лишь мешаем их основным параметрам данными глобального состояния. - Во-вторых, глобальное состояние зачастую обладает сложной структурой. Это может быть не только простая переменная, но и большой объект или массив данных.

Тогда все компоненты веб-приложения могли бы легко взаимодействовать с общим состоянием — подобно тому, как модули обмениваются информацией.

![](https://pictures.s3.yandex.net:443/resources/Frame_1562_1_1709306740.png)

Да, компоненты смогут не только получать данные в нужный момент, но и изменять их. При этом все остальные компоненты будут непрерывно следить за изменениями глобального состояния и мгновенно реагировать на новые данные.

Именно такой подход мы будем использовать в веб-приложении Pindie. Компонент `AuthForm` при авторизации пользователя передаст его данные в глобальное состояние, а остальные компоненты, заметив это, смогут внести нужные изменения. Компонент `Header` будет отображать в кнопке текст `Выйти` вместо `Войти`, не отправляя повторных запросов для проверки авторизации, а ориентируясь только на данные глобального состояния. По тому же принципу детальная страница игры уберёт атрибут `disabled` у кнопки голосования, сделав её доступной авторизованному пользователю.

Подготовка проекта

Идея глобального состояния широко используется веб-разработчиками. За время развития React было придумано множество способов его реализации. В следующих уроках мы рассмотрим наиболее популярные варианты, но перед этим необходимо подготовить Pindie. Поможем тебе сделать это и за четыре шага создать методы работы с глобальным состоянием.

Шаг 1. Создание хранилища `App.jsx`

Хук `useState` в React работает только в клиентских компонентах. Это значит, что для взаимодействия с глобальным состоянием между корневым компонентом `RootLayout` и остальными компонентами веб-приложения необходимо создать промежуточный клиентский компонент `App`. Он будет выступать в роли хранилища глобального состояния, а также позволит компонентам изменять его, используя нужные методы.

Создай файл `App.jsx` в директории `app` и обязательно укажи тип компонента👇🏻

"use client"

Чтобы глобальное состояние было доступно всем компонентам, хранилищу `App` нужно частично взять на себя роль `RootLayout` и отображать базовый шаблон сайта: шапку, активную страницу (роут) и подвал. Для этого импортируй `Header` и `Footer`, а также укажи компоненту `props` принимать `children` — активную страницу👇🏻

"use client"
import { Header } from "./components/Header/Header";
import { Footer } from "./components/Footer/Footer";

export const App = (**props**) => { }

Создай JSX-разметку, подобную компоненту `RootLayout`, и не забудь про основные правила JSX.

Чтобы всё отображалось правильно, оберни компоненты во фрагмент `<></>`👇🏻

export const App = (props) => {
	**return (
    <>
      <Header />
      {props.children}
      <Footer />
    </>
  );**
}

Шаг 2. Модификация `layout.js`

Теперь нужно интегрировать компонент между `RootLayout` и другими компонентами. Для этого импортируй `App` в `layout.js` и поменяй разметку внутри 👇🏻

import "./globals.css";
import { App } from "./App";

export const metadata = {
  title: "Pindie",
  description: "Портал инди-игр от студентов Яндекс Практикума",
};

export default function RootLayout({ children }) {
  return (
    <html lang="ru">
      <body>
        <App>{children}</App>
      </body>
    </html>
  );
}

Так как мы перенесли шапку и подвал в новый компонент, можешь удалить их импорты из файла `layout.js` и сами компоненты из разметки. Вместо них между `body` и `children` размести компонент `App`. Таким образом, все дочерние компоненты `RootLayout` будут обёрнуты в `App` — общее хранилище, где им будет доступно глобальное состояние.

Теперь можно переходить к самому интересному — созданию глобального состояния.

Шаг 3. Создание глобального состояния

Глобальное состояние — это не единая переменная, а набор данных и методов для их изменения. Импортируй всё необходимое:

- Хуки `useState` и `useEffect` из библиотеки React. Хук `useState` понадобится для объявления состояний, а `uesEffect` — для проверки авторизации пользователя при каждом запуске веб-приложения. - Функции `getJWT`, `setJWT`, `removeJWT` и `getMe` из файла `api-utils.js`. Все они позволят манипулировать `JWT`-токеном, а последняя — получать данные пользователя. - Эндпоинты API — объект `endpoints` из файла `config.js`. Этот объект состоит из маршрутов API, к которым мы будем обращаться, отправляя запросы.

Проверяй 👇🏻

"use client"
import { Header } from "./components/Header/Header";
import { Footer } from "./components/Footer/Footer";

// Импорты для работы с глобальным состоянием
import { useEffect, useState } from "react";
import { getJWT, setJWT, removeJWT, getMe } from "./api/api-utils";
import { endpoints } from "./api/config";

Теперь создай три основных состояния, которые нужны всему веб-приложению 👇🏻

export const App = (**props**) => {
	const [isAuth, setIsAuth] = useState(false);
  const [user, setUser] = useState(null);
  const [token, setToken] = useState("");

	return (
    <>
      <Header />
      {props.children}
      <Footer />
    </>
  );
}

- Состояние `isAuth` будет хранить статус авторизации. По умолчанию пользователь не будет авторизован, поэтому хук принимает значение `false`. При авторизации `isAuth` изменится, сообщая всему веб-приложению, что пользователь авторизовался. - Состояние `user` будет хранить объект с данными пользователя. По умолчанию пользователь ещё не авторизовался и его данных у веб-приложения нет, поэтому хук принимает значение `null` - Состояние `token` будет хранить `JWT`-токен авторизованного пользователя. Здесь ситуация повторяется: пока пользователь не авторизован, его токен по умолчанию принимает значение пустой строки `“”`

Шаг 4. Создание методов работы с глобальным состоянием

При авторизации пользователя в Pindie нужно, чтобы все компоненты узнавали об этом и могли изменять своё поведение.

Создай метод `login`, который будет принимать параметры `user` и `token`👇🏻

const login = (user, token) => {
	setIsAuth(true);
  setUser(user);
	setToken(token);
	setJWT(token);
};

Этот метод позволяет установить следующие значения:

- Состояние авторизации пользователя — `isAuth` (при авторизации функция `setIsAuth` будет принимать значение `true` и сохранять его в глобальное состояние). - Данные пользователя — `user` (при авторизации функция `setUser` будет принимать данные пользователя в виде объекта и сохранять в глобальное состояние). - `JWT`-токен пользователя — `token` (при авторизации функция `setToken` будет принимать токен пользователя в виде строки и сохранять в глобальное состояние). - Функция `setJWT`, которую мы импортировали из файла `api-utils.js`, позволит записать `JWT`-токен в память браузера (а именно в `localStorage`).

Создай метод `logout`. Он будет выполнять противоположные действия метода `login` и сбрасывать глобальное состояние, удаляя все данные 👇🏻

const logout = () => {
	setIsAuth(false);
	setUser(null);
	setToken("");
	removeJWT();
}

Здесь вместо функции `setJWT` мы используем `removeJWT`, чтобы удалить токен пользователя из памяти браузера, после того как он решит выйти из своего аккаунта.

Для проверки авторизации пользователя нужно создать асинхронную функцию `checkAuth`👇🏻

const checkAuth = async () => {
	const token = getJWT();
	if (token) {
		const me = await getMe(endpoints.me, token);
		if (me) {
			login(me, token);
		} else {
			logout();
		}
	}
}

Этот метод работает следующим образом:

1. Функция `getJWT` проверяет наличие `JWT`-токена в памяти браузера. 2. Только если токен существует, метод переходит к его проверке. Для этого функция `getMe` отправляет запрос к API и сравнивает токен из браузера с токеном в базе данных. Из урока «Запросы с `JWT`-токеном и его хранение» ты знаешь, что у каждого `JWT`-токена есть свой срок жизни. 3. Если токены не совпадают, значит, в базе данных он обновился на новый, а в браузере остался устаревший. В этом случае вызывается метод `logout` и глобальное состояние сбрасывается, удаляя из себя все данные. 4. Если же токены одинаковы, вызывается метод `login`, который записывает данные пользователя в глобальное состояние.

Проверять правильность JWT-токена следует при каждом запуске веб-приложения. Это делает его работу более безопасной. В случае, если пользователь давно не заходил в свой аккаунт, веб-приложение попросит сделать это снова, удалив все старые данные из глобального состояния, а старый токен — из памяти браузера. Если же пользователь авторизовался совсем недавно, ему не придётся это делать при каждом запуске Pindie или обновлении сайта. Благодаря такой проверке веб-приложение будет самостоятельно записывать данные пользователя в глобальное состояние.

Для того чтобы проверка осуществлялась только при запуске Pindie, пригодится хук `useEffect`, который мы уже импортировали 👇🏻

useEffect(() => {
	async function check() {
		await checkAuth();
	};
	check();
}, []);

Внутри хука мы создаём асинхронную функцию, внутри которой запускаем проверку `checkAuth`. В качестве зависимостей хука указан пустой массив. Это позволит запустить его только при монтировании компонента `App`, а значит, при монтировании всего веб-приложения.

Можно убедиться в работе функции, переходя по адресу [localhost:3000](http://localhost:3000){target="_blank"} из разных вкладок или просто обновляя страницу. Если пользователь уже авторизован, при каждом открытии и обновлении вкладки глобальное состояние будет хранить наши данные.
