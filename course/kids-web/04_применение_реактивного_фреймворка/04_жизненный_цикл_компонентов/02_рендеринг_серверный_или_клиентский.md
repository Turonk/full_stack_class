# Рендеринг: серверный или клиентский

## Что делает `Next.js` в проекте

В модулях про вёрстку и JS для запуска проектов мы просто открывали файл `index.html` в браузере либо использовали расширение Live Server — локальный сервер, который помогал обновлять страницу при изменениях кода. Проекты состояли из нескольких файлов, и всем управляли HTML, CSS, JavaScript. 

Теперь, чтобы запустить проект, каждый раз открываем VS Code, вводим команду `npm run dev`. В терминале бегут какие-то строчки кода 👇🏻

![](https://pictures.s3.yandex.net:443/resources/Frame_1487_1_1707502405.png)

И проект запускается в браузере по адресу [localhost:3000](http://localhost:3000){target="_blank"}. 

На странице формируется интерфейс приложения из React-элементов. А для всех необходимых библиотек и команд есть отдельный файл `package.json` 👇🏻

```JSON
{
  "name": "pindie-theme-1",
  "version": "0.1.0",
  "private": true,
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "lint": "next lint"
  },
  "dependencies": {
    "react": "^18",
    "react-dom": "^18",
    "next": "14.0.4"
  }
}
```

В разделе зависимостей `dependencies` хранится перечень библиотек: `react` и `react-dom` тебе знакомы. Они отвечают за отображение элементов страницы. Но вот за что отвечает `next`? 

Next.js — полноценный фреймворк, который дополняет и улучшает проекты с использованием React.

Принцип React-приложений — отдать минималистичный HTML-файл и много JavaScript-кода. Пользователь должен разом загрузить весь код и за счёт вызова функций построить весь интерфейс программы в браузере устройства. 

У такого подхода есть ряд недостатков, их можно компенсировать за счёт взаимодействия с сервером. Next.js позволяет подготавливать данные и интерфейс страницы до того, как они попадут к пользователю. Фреймворк разделяет код проекта на серверные компоненты и клиентские. Поэтому давай зафиксируем:

- React отвечает за проект на клиенте — код, выполняемый браузером.
- Next.js помогает подготовить часть проекта до попадания на клиент — назовём это серверной частью.

## Разновидности подходов

Развитие современных технологий, увеличение объёма оперативной памяти устройств позволили переложить выполнение программы **на сторону клиента,** сделать интерфейсы интересными, создавать интерактивные элементы и выполнять более сложные вычисления. 

Если раньше загрузку каждой статичной страницы с разметкой сайта нужно было ждать, то современные приложения (навигаторы, социальные сети, стриминговые платформы) могут молниеносно перестраивать интерфейс на устройстве пользователя, взаимодействовать с серверами и параллельно обрабатывать большое количество данных. 

Для разработки усложнившихся элементов интерфейса стали использовать библиотеку React — её популярность росла, и теперь большинство современных сайтов и приложений разработаны с её помощью.

Пользуясь подобными сайтами, юзер при первом запросе загружает небольшой HTML-файл, который тянет за собой море JavaScript-кода. Этот код выполняется браузером, и всё приложение собирается непосредственно у пользователя на устройстве. Этот подход породил **одностраничные приложения (сокращённо SPA).**

Аски, а ты в тему! Проект, который мы делали с тобой — многостраничный сайт с кроссовками — при переходе между страницами загружал готовую вёрстку **с сервера.** В зависимости от качества связи и мощности устройств такие загрузка и отображение разных страниц могут занимать много времени. Избавиться от лишних запросов к серверу и перезагрузки страницы как раз помогает React. 

SPA за счёт JavaScript-кода позволяет:

- перестраивать вёрстку страницы, имитируя переходы, как в многостраничном сайте
- делать приложение модульным
- обновлять часть страницы и проще взаимодействовать с DOM-элементами

Таким образом, ты можешь смотреть 4К-стрим, переписываться в чате, перемещаться между страницами сайта и видеть дополнительную информацию в отдельных блоках с виджетами. И всё это реализовано на устройстве пользователя в одном HTML-файле.

![](https://pictures.s3.yandex.net:443/resources/Frame_1481_1_1707502530.png)

Но SPA имеет и ряд минусов:

- Увеличивает объём кода, негативно влияя на скорость его скачивания и обработки на устройстве пользователя
- Не даёт приложению работать в браузере с отключённым JavaScript
- Ухудшает поисковую выдачу
Поисковые сервисы анализируют HTML-файл с интерфейсом сайта — ключевую информацию и теги. SPA строят интерфейс после загрузки кода в браузере пользователя, а значит, до этого момента поисковым сервисам просто нечего анализировать, исходная HTML-страница SPA содержит минимум информации.

Существует способ избавиться от этих минусов — заранее сформированная HTML-страница с минимально необходимыми данными и тегами. Такой подход называется **серверным рендерингом,** или **server-side rendering (SSR).**

Фреймворк Next.js создан относительно недавно, но быстро стал популярным за счёт работы с server-side render приложениями, написанными на React. 

Главное его отличие от SPA с использованием React — в способе рендера конечных веб-страниц. Если React загружает минимальный HTML и большой блок JS-кода, то Next.js использует тот же React для server-side rendering — формирования первоначального HTML на стороне сервера. В процессе он оптимизирует код так, чтобы не отправлять сразу на клиентскую сторону больше кода, чем действительно необходимо для конкретной страницы, а просто подгружает его позже.

## Разновидности компонентов

Любой сайт имеет ключевые особенности — даже главная страница Яндекса.

![](https://pictures.s3.yandex.net:443/resources/Frame_1479_1_1707502622.png)

Тут HTML-страница (а именно тег `head` и его наполнение, логотип и поисковая строка с основными CSS-свойствами) формируется на сервере при помощи SSR. А все второстепенные блоки (виджет погоды, блок рекламы или подборка из Маркета) — на клиенте, как SPA. И всё это из компонентов, написанных при помощи React.

Изначально Next.js разрабатывался для создания SSR-страниц, поэтому компоненты, созданные в Next.js, считаются серверными. 

Код в таких компонентах будет обрабатываться на сервере, а это накладывает свои ограничения 👇🏻

- Нет возможности работать с инструментами браузера (такими, как событие `click`).
- Недоступен объект `window` браузера и все его полезные свойства и методы:
    
    а) `console` — объект консоли, обеспечивающий доступ к консоли браузера
    
    b) `document` — ссылка на объект, содержащий DOM-элементы страницы в браузере
    
    с) `localStorage` — объект хранилища в браузере, используемый для хранения данных
    
- Нет доступа к API браузера — важным инструментам:
    
    a) Fetch API, позволяющему отправлять запросы
    
    b) Web Audio API, позволяющему работать с видео- и аудиоконтентом
    
    с) Notifications API, позволяющему веб-страницам контролировать отображение системных уведомлений
    

Но у серверных компонентов имеются и преимущества:

- Есть прямой доступ к серверу, что упрощает часть вычислений.
- Можно обезопасить секретные данные приложения.
Они останутся на сервере, к которому у пользователя нет доступа. Если бы секретные данные отправлялись по сети или хранились на устройстве пользователя, их было бы проще украсть.
- Можно хранить часть библиотек, используемых в проекте, на сервере и уменьшить объём скачиваемых пользователем данных.

Новый JSX-файл в проекте на Next.js по умолчанию считается серверным. Но есть и волшебная фраза, чтобы попросить компонент быть таким: `use server`. Её необходимо указывать в самом начале файла, на первой строке — так Next.js понимает, что компонент должен использоваться согласно подходу SSR.

Чтобы React-код обрабатывался, как SPA, в браузере пользователя и получил доступ ко всем браузерным технологиям и элементам страницы, необходимо указать на первой строке `use client` — ключевую фразу для Next.js 👇🏻

![](https://pictures.s3.yandex.net:443/resources/Snimok_ekrana_2024-01-11_v_00.52.33_1707502637.png)

Чтобы увидеть разницу в серверном и клиентском компонентах, достаточно вызвать `console.log()`

Код клиентского компонента выполняется в браузере, поэтому сообщение выводится в консоль браузера 👇🏻

Серверные компоненты обрабатываются с помощью Next.js до браузера, поэтому аналогичное сообщение можно увидеть в терминале на этапе сборки проекта 👇🏻

Любые сайты или приложения полноценно оживают только при взаимодействии с ними. Покупая товары на маркете, используя музыкальный или видеосервис, переписываясь в мессенджерах, ты видишь, как изменяются их элементы: заменяется текст в блоках, осуществляются переходы между страницами, изменяются и отображаются данные в понятном человеку виде (списки, графики, таблицы, различные карточки и блоки), происходит анимированная загрузка или скачивание контента.

Вся эта динамика доступна благодаря браузеру и особенностям языка программирования. Поэтому, разрабатывая проект, мы больше сконцентрируемся **на клиентских компонентах** и создадим **интерактивный интерфейс для Pindie.**
