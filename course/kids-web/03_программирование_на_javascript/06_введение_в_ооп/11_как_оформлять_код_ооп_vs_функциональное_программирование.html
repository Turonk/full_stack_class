Как оформлять код (ООП vs функциональное программирование)

Нет причин переживать! Разработчики давно столкнулись с этой проблемой. Код можно и нужно объединять в логические блоки и как-то структурировать. Так были придуманы правила, которых следует придерживаться при написании кода.

Чтобы разобраться в том, какие два вида правил для написания кода существуют, посмотрим, как Цэ-эс-эсочка просит Аски принести кофе.

Чтобы Аски принёс Цэ-эс-эсочке нужный кофе, необходимо передать ему инструкцию.

Первый вариант — описать в деталях последовательность действий: сколько взять зерна, как молоть, воду какой температуры использовать, что добавлять и так далее.

Второй — просто назвать конкретный вариант кофейного напитка.

![](https://pictures.s3.yandex.net:443/resources/Untitled_Artwork_630_1705331773.png)

Обе инструкции правильные, но есть огромное отличие.

Первая инструкция объясняет, **как** приготовить кофе (такой стиль объяснения называют **императивным**). Вторая — **что** нужно получить в результате (это **декларативный** стиль).

Конечно! Ниже напишем код для умножения элементов массива на два.

Императивный вариант с подробной инструкцией, **как** это сделать 👇🏻

function multiplyBy2(array) { // Умножить на два
	const result = [];

  for (let i = 0; i < array.length; i++) {
	  const element = array[i];
    const multiplyBy2Element = element * 2;
    result.push(multiplyBy2Element);
  }

  return result;
}

Декларативный вариант с описанием того, **что** нужно получить 👇🏻

function multiplyBy2(array) {
    return array.map((element) => element * 2);
}

В первом варианте все детали мы описываем сами, во втором — они скрыты от нас.

- Если нужно разработать уникальный алгоритм и детально описать какое-то действие, то подходит первый вариант (например, для построения маршрута на карте с учётом пробок, поиска информации в большом объёме данных, процесса отрисовки динамических элементов сайта). - Если описываем логику программы, то лучше писать, как во втором варианте, а детали реализации скрыть внутри (именно так написаны современные интерфейсы приложений).

И да — для каждого подхода есть свой набор правил, которые помогают организовать код безупречно.

Объектно-ориентированное программирование

Самый популярный набор правил для написания императивных алгоритмов-инструкций — объектно-ориентированное программирование (ООП). По названию можно догадаться, что правила касаются работы с объектами.

ООП подходит для использования большого количества объектов и описания их взаимодействия. При этом внутри ООП есть всего три правила — их называют принципами ООП: наследование, инкапсуляция и полиморфизм.

Понимаем, звучит сложно, но вот увидишь, мы уже применили их в проекте `Heroes Dance Battle`

Наследование

Наследование в ООП тебе уже знакомо, урок с таким названием был на предыдущей неделе. Коротко напомним, что это возможность создавать классы на основе других.

В танцевальном проекте мы использовали класс `Hero` в качестве родительского для создания классов рыцаря `Knight` и мага `Mage`. Так от класса-родителя наследовались общие принципы, а мы описывали только отличительные черты каждого нового класса.

Этот принцип позволяет избавиться от дублирования однотипного кода.

Инкапсуляция

Суть принципа инкапсуляции в том, что после создания класс хранит всю необходимую информацию об описываемой сущности (персонаж игры, кнопка на сайте и так далее) — в итоге, его свойства и методы в одном месте. Разработчик решает, что будет внутренней логикой, а что доступно другим частям программы. Поэтому в других частях программы достаточно использовать экземпляр класса, его свойства и методы, не разбираясь в их внутреннем устройстве и не переписывая код специально под новое место.

Вот тебе пример из знакомого кода. В классе `Hero` проекта `Heroes Dance Battle` у персонажа есть имя и его характеристики, а также метод `displayHero()`, который выводит данные о герое в консоль. Другие части программы не волнует, как хранятся эти свойства и реализован метод. Свойства и методы не нужно записывать заново — просто передаёшь необходимые данные в класс и используешь полученный объект в программе.

Представь, что машина — это объект. Её методы: `ехать`, `тормозить`, `поворачивать`. Полиморфизм

Полиморфизм — это принцип ООП, при котором не нужно создавать для каждого класса отдельный метод, который бы делал одно и то же. Достаточно реализовать метод так, чтобы он был универсальным.

Для примера снова обратимся к методу `displayHero()`, который выводил данные о персонаже в консоль. Ты ведь помнишь , что мы вызывали его и у объектов с классом `Hero`, и у дочерних классов `Knight` и `Mage`. Получается, хоть все объекты были разными, им одинаково подходил `displayHero()`, настолько он был гибким.

{quiz-task} background: | #f5f6f7 content: | 🚗 Давай опять визуализируем принцип с помощью машины. Методы `ехать` и `заправить бак` должны быть универсальны как для автобуса, так и для спорткара. Но работать при этом они будут по-разному: спортивная машина едет в разы быстрее автобуса, а топливный бак общественного транспорта должен вмещать больше топлива. {/quiz-task}

Функциональное программирование

Здесь из названия ясно, что правила основаны на работе с функциями.

Ты уже знаешь, что в аргументы функциям можно передавать простые значения: строки, числа и логический тип данных. Однако на этом возможности функций не ограничиваются.

В этом подходе очень часто функции передаются внутрь других функций. Получается некая матрёшка из функций (например, функция создания страницы будет вызывать функцию, которая строит шапку сайта, а она, в свою очередь, вызовет функцию создания логотипа и кнопок, которые есть внутри шапки сайта). Так строится большинство современных сложных веб-сайтов.

В следующих уроках потренируемся писать код по правилам функционального программирования (тем более с инструкциями и ООП мы уже много работали до этого), к тому же в новом модуле ты познакомишься с фреймворком React, работа с которым как раз основана именно на этом подходе.

А пока давай убедимся, что ты понимаешь, в чём разница в упомянутых сегодня подходах к программированию.
