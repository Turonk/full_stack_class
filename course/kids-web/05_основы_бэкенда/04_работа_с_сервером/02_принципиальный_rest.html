Что такое API

API можно представить как набор инструкций, которые разработчики используют для взаимодействия с определённой системой. Само понятие **API** (application programming interface) переводится как **программный интерфейс приложения.**

{quiz-task} background: | #f1f1ef content: | ❗ Запомни, API = программный интерфейс. {/quiz-task}

Да, точно так же и API даёт разработчику возможность управлять определённой системой, не вдаваясь в её внутреннее устройство. Он есть практически у всего, особенно в мире веб-разработки. Когда мы пользуемся сайтом, общение происходит с его сервером через API.

На самом деле маршруты, которые мы создаём, — это и есть тот самый набор инструкций, то есть команд, которые нужно выполнить, чтобы получить желаемый результат.

API есть даже у библиотек, которыми мы пользуемся. Инструкции по работе с ним указаны в официальной документации. К примеру, библиотека Mongoose, которую мы активно юзали в прошлой теме, предоставляет нам методы для работы с базой данных. Эти методы — её интерфейс взаимодействия.

Эволюция веб-разработки

Мы знаем, как работают наши браузеры и как они позволяют пользоваться сайтами. При переходе на адрес сайта из нашего браузера отправляется запрос к серверу, на котором он хранится. Сервер, в свою очередь, генерирует и возвращает готовые HTML-страницы сайта, его CSS-стили и JS-скрипты, и вот, сайт перед нами.

Когда речь идёт об одностраничном сайте, этот подход показывает себя наилучшим образом. Но, когда мы говорим о больших многостраничных или динамичных сервисах, проявляется одна из его главных проблем — **необходимость перезагрузки.** При каждом переходе с одной страницы на другую браузер полностью перезагружает сайт, а сервер заново генерирует HTML-страницы.

Также важно понимать, что HTML-страницы предназначены для отображения в браузере. Многие сервисы сейчас не останавливаются на веб-версии, и у большинства из них есть свои мобильные приложения. Они устроены иначе и не используют HTML-код, обладая совершенно другой структурой. Учитывая это, разработчикам сервиса нужно создавать отдельное API, которое будет выполнять те же действия, но для мобильных приложений.

![](https://pictures.s3.yandex.net/resources/1_1_1714758711.jpg)

Учитывая эти недостатки, разработчики придумали новый подход. Теперь API может использоваться для всех платформ, включая сайты, мобильные приложения или программы, установленные на компе. При таком подходе сервер отправляет только данные, а клиент самостоятельно решает, как их отображать. Теперь сайты могут встраивать данные в готовый HTML или использовать отдельные шаблоны.

Когда API стали более гибкими и стали возвращать только нужные данные, появилась необходимость в том, чтобы задать определённые правила. Для сохранения гибкости API и его универсальности для разных платформ были придуманы специальные методы создания API. Проще говоря, это набор правил, которых разработчику нужно придерживаться при работе с API. Один из таких методов — **REST,** с которым мы сейчас познакомимся.

Что такое REST

**REST** — это набор правил, по которым создают API. Когда API разрабатывается в соответствии с этими принципами, его называют **REST API.**

{quiz-task} background: | #f1f1ef content: | ❗ Важно понимать, что REST — это просто подход к написанию кода, своего рода стиль, который помогает разработчикам создавать мощные и легко масштабируемые бэкенд-приложения. {/quiz-task}

Принципы REST позволили отделить клиента от сервера. Теперь серверу не важно, с чем взаимодействовать: с сайтом или веб-приложением, с мобильным или десктоп-приложением. Именно благодаря этому REST считается одним из самым популярных подходов к разработке API. Давай познакомимся с его принципами.

Принципы REST

Принцип 1. Клиент — сервер

Этот принцип отделяет клиента и сервер друг от друга. Следуя ему, сервер отвечает за работу с данными и в некоторых случаях за их хранение. Он не генерирует HTML-страницы для сайта и занимается только работой с данными и никак не затрагивает интерфейс.

В то же время клиент отвечает за пользовательский интерфейс, как наше приложение Pindie на React. Кроме того, клиент запрашивает у сервера те самые данные или отправляет ему свои и просит с ними что-то сделать.

Получается структура, при которой клиент отправляет запрос на сервер, а в ответ получает нужные ему данные. Этот принцип позволяет создавать клиента и сервер отдельно друг от друга, что сильно ускоряет разработку.

Принцип 2. Отсутствие состояния

Это один из самых важнейших принципов, указывающий на то, что каждый запрос от клиента должен содержать всю информацию, которая нужна для его обработки.

Благодаря принципу отсутствия состояния не нужно хранить лишние данные о прошлых обращениях каждого из клиентов. Достаточно обработать запросы по отдельности, но для этого серверу нужна соответствующая информация.

Принцип 3. Единый интерфейс

Важно, чтобы у API был единый способ получения данных. Этот принцип проще всего понять на примере обращения к интерфейсу. К примеру, если тебе нужна информация о доступных играх, отправь `GET`-запрос по определённому адресу 👇🏻

https://my-server.ru/api/games

Ответ от сервера придёт в формате JSON, содержащем запрашиваемые данные.

Теперь представь, что мы добавили нашему сайту раздел с продажей игровых клавиатур и создали для этого отдельный каталог. Для получения информации о клавиатурах снова отправь `GET`-запрос, только изменив эндпоинт 👇🏻

https://my-server.ru/api/keyboards

Сервер обработает этот запрос так же, как и предыдущий, и вернёт ответ в формате JSON.

Принцип 4. Многоуровневая система

Первый принцип REST подразумевает, что обмен данными происходит только между клиентом и сервером. Мы можем не нарушать этот принцип и при этом расширить возможности нашего API.

Между клиентом и основным сервером могут находиться промежуточные серверы, которые выполняют различные задачи, такие как {{кеширование}}[web_teens_theme4_lesson_2_кеширование] или {{балансировка нагрузки}}[web_teens_theme4_lesson_2_балансировка нагрузки]. Также наш сервер может общаться с другими серверами, чтобы дополнить свои возможности.

К примеру, если у нас есть промежуточный сервер, клиент сначала отправляет запрос ему, а затем этот сервер передаёт его дальше по цепочке основному серверу. Такой же обратный последовательный путь совершит и ответ. В этом случае промежуточный сервер действует как клиент для основного сервера, и каждому в этой цепочке известно только о своих соседях справа и слева и ничего о полном пути запроса.

![](https://pictures.s3.yandex.net/resources/3_1714758736.jpg)

Осталось ещё два принципа!

Принцип 5. Кеширование

Иногда клиент повторно запрашивает одни и те же данные с сервера — к примеру, когда мы постоянно заходим на страницу одной и той же игры в Pindie.

Это означает, что часть данных может быть сохранена в памяти. И если клиенту эта информация вновь понадобится, то новый запрос на сервер можно не делать, а взять всё из памяти.

Следуя этому принципу, важно не кешировать всё подряд. Например, в приложении Pindie может быть сотня или тысяча игр, а памяти для хранения их всех может и не быть. Также некоторые данные со временем могут устаревать — как вариант, число голосов за игру. Их нет смысла кешировать, так как они самостоятельно постоянно обновляются.

Принцип 6. Код по запросу

Этот принцип позволяет серверу отправлять на клиент исходный код, который затем будет выполняться на стороне клиента. То есть сервер может отправить целые сценарии, к примеру, на хорошо тебе знакомом JavaScript.
