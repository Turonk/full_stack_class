Зона для админов

Да, страница с формой авторизации, которая отображается по умолчанию, теперь доступна только неавторизованным пользователям.

Авторизованные пользователи даже при большом желании не смогут попасть на эту страницу, так как авторизация проверяется ещё до того, как страница отправится на клиент для отображения.

![](https://pictures.s3.yandex.net/resources/zone_1714999555.jpg)

Отправляем админку

В проекте уже есть функция `sendIndex`. Она отвечает за выдачу страницы с формой авторизации для пользователей, которые ещё не залогинились.

Чтобы попасть на неё, после перенаправления на `/admin/dashboard` приходится возвращаться на главный маршрут `/`, и только тогда можно увидеть заветную страницу админки.

Добавь отдельную функцию `sendDashboard`, которая примет на себя ответственность за выдачу страницы админки, чтобы этим не занималась функция `sendIndex`. Функцию можно создать прямо в контроллере авторизации, в файле `auth.js` папки `controllers` 👇🏻

// Другие функции-контроллеры

const sendDashboard = (req, res) => {
  res.sendFile(path.join(__dirname, "../public/admin/dashboard.html"));
};

Всё, что делает функция, — обращается к объекту ответа `res` и, вызывая метод `sendFile`, отправляет страницу админки. Для указания точного и безопасного пути используется встроенный модуль `path`. Его метод `join` склеивает пути, создавая итоговый маршрут до HTML-файла страницы.

Распределяем задачи

Теперь нужно изменить функцию `sendIndex`. Посмотри, как она выглядит сейчас 👇🏻

const sendIndex = (req, res) => {
  if (req.cookies.jwt) {
    try {
      jwt.verify(req.cookies.jwt, "some-secret-key");
      return res.sendFile(
        path.join(__dirname, "../public/admin/dashboard.html")
      );
    } catch (err) {
      res.sendFile(path.join(__dirname, "../public/index.html"));
    }
  }
  res.sendFile(path.join(__dirname, "../public/index.html"));
};

Если в запросе переданы куки и в куках есть `JWT`-токен пользователя, да и к тому же он правильный и не просрочен, функция отправляет страницу админки и завершает свою работу, а вместе с тем и запрос.

Выдачей страницы админки теперь занимается функция `sendDashboard`. Лучшим вариантом здесь будет перенаправлять пользователя на маршрут `/admin/dashboard`, провоцируя тем самым новый запрос. Измени код функции `sendIndex`, используя новый метод `redirect` вместо метода `sendFile` для страницы админки 👇🏻

Метод `redirect` встроен в объект ответа `res` и используется для перенаправления пользователя на другой URL-адрес. Когда сервер отправляет ответ с перенаправлением (методом `redirect`), браузер автоматически делает новый запрос по маршруту, указанному в перенаправлении. Перенаправление заставит браузер выполнить новый запрос по маршруту `/admin/dashboard`, а это именно то, что нам нужно 👇🏻

const sendIndex = (req, res) => {
  if (req.cookies.jwt) {
    try {
      jwt.verify(req.cookies.jwt, "some-secret-key");
      return res.redirect("/admin/dashboard");
    } catch (err) {
      res.sendFile(path.join(__dirname, "../public/index.html"));
    }
  }
  res.sendFile(path.join(__dirname, "../public/index.html"));
};

Теперь ещё раз посмотри, как это работает для уже авторизованного пользователя 👇🏻

1. Авторизованный пользователь открывает интерфейс твоего приложения, переходя по адресу `localhost:3000`. При этом он запрашивает у сервера страницу с формой авторизации. 2. Получив этот запрос, роутер, отвечающий за выдачу страниц, передаёт запрос контроллеру `sendIndex` 3. Контроллер проверяет куки и `JWT`-токен пользователя внутри них. А после успешного завершения понимает, что пользователь уже авторизован и отправлять ему страницу с формой авторизации ещё раз не нужно. 4. Тогда контроллер берёт и принудительно перенаправляет пользователя со стартовой страницы `localhost:3000` на страницу админки `localhost:3000/admin/dashboard`. Получается, что в процессе перенаправления клиент отправляет серверу ещё один запрос, но уже с целью получить страницу админки.

Клуб админов

В роутере, принимающем запросы на страницы, добавь обработку нового маршрута 👇🏻

// routes/pages.js
// Импорты и другие маршруты

pagesRouter.get("/admin/**", sendDashboard);

Здесь в качестве маршрута сначала указываешь родительский маршрут `/admin`, а затем конструкцией `/**` всевозможные дочерние. Это значит, что роутер сможет обрабатывать не только запросы по маршруту `/admin/dashboard`, но и любые другие маршруты, начинающиеся с `/admin`. Для перехода на страницу админки тебе необязательно указывать полный путь `/admin/dashboard`, достаточно будет только `/admin`. Также это отличная возможность предотвратить опечатки в ссылках, если, к примеру, в слове `dashboard` будет допущена ошибка.

При желании в будущем можно расширить зону для админов и добавить дополнительные страницы, к примеру `/admin/settings` или `/admin/secure`

Фейсконтроль

Исправить проблему поможет добавление миддлвара, который будет проверять `JWT`-токен пользователя в куки и не пускать посторонних в закрытый клуб админов.

Первый миддлвар создашь самостоятельно: он будет проверять наличие токена в куки и, если он есть, записывать в специальный заголовок, передавая управление над запросом второму миддлвару. Если токена не будет, миддлвар завершит запрос, принудительно перенаправив пользователя обратно на страницу с формой авторизации.

Второй миддлвар у тебя уже готов — `checkAuth`. Вспомни, как работает эта функция 👇🏻

- Достаёт из заголовков запроса заголовок авторизации — `authorization`, в котором хранится `JWT`-токен пользователя. - Затем чистит токен от мусора, удаляя `Bearer` и пробел после него. - После верифицирует токен, проверяя срок его действия и принадлежность конкретному пользователю. - При успешной верификации записывает расшифрованные данные из токена в объект запроса `req.user` и передаёт запрос следующему миддлвару.

Получается, что `checkAuth` комплексно проверяет авторизацию пользователя. Всё, что нужно для этого, — заранее установить заголовок `authorization` в объекте запроса.

Предлагаем заняться этим в первом миддлваре, который будет самым первым принимать запрос на страницу админки. Сначала создай функцию `checkCookiesJWT` в миддлваре авторизации, в файле `auth.js` папки `middlewares` 👇🏻

// Импорты и другие миддлвары
const checkCookiesJWT = (req, res, next) => {};

Первым делом проверь: есть ли куки в объекте запроса и есть ли в них поле с `JWT`-токеном 👇🏻

// Импорты и другие миддлвары

const checkCookiesJWT = (req, res, next) => {
  if (!req.cookies.jwt) {
    return res.redirect("/");
  }
};

В случае, если в куках нет токена, заверши работу функции, перенаправив пользователя обратно на страницу с формой авторизации.

Но, если токен будет, запиши его в тот самый заголовок `authorization`, чтобы он стал доступен миддлвару `checkAuth`, который примется за запрос сразу после работы этого миддлвара 👇🏻

// Импорты и другие миддлвары

const checkCookiesJWT = (req, res, next) => {
  if (!req.cookies.jwt) {
    return res.redirect("/");
  }
  req.headers.authorization = `Bearer ${req.cookies.jwt}`;
  next();
};

Так как функция `checkAuth` ждёт токен в формате `Bearer сам_токен`, запиши токен из куки именно в таком формате. Не забудь вызвать метод `next()` в конце функции, чтобы обработка запроса пошла дальше по цепочке миддлваров.

Всё, что тебе осталось сделать, — донастроить роутер для обработки запросов по маршруту `/admin`, добавив перед контроллером нужные миддлвары 👇🏻

// routes/pages.js
// Импорты и другие маршруты

pagesRouter.get("/admin/**", checkCookiesJWT, checkAuth, sendDashboard);

Итак, при получении запроса по маршруту `/admin`, миддлвар `checkCookiesJWT` начнёт его обработку. Он проверит, есть ли в куки `JWT`-токен, и запишет его в специальный заголовок авторизации, передав управление следующему миддлвару. Затем миддлвар `checkAuth` прочитает содержимое заголовка, почистит его от лишнего и провалидирует сам токен, как он привык это делать обычно.

Если с токеном всё гуд, запрос перейдёт контроллеру `sendDashboard`, который со спокойной душой отправит на клиент страницу админки.
