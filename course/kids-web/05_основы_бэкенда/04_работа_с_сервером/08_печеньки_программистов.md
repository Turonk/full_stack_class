# Печеньки программистов

![](https://pictures.s3.yandex.net/resources/cookie_1714986372.jpg)

Для начала разберёмся, как должен работать весь процесс авторизации 👇🏻

1. Заполненные данные из формы на клиенте отправятся в виде запроса на сервер к функции `login`, которая и должна провести авторизацию. 
2. Функция `login` начнёт искать пользователя с указанным логином и паролем в базе данных и, если найдёт, сгенерирует для него уникальный `JWT`-токен, который отправит в ответе на клиент вместе с данными самого пользователя. 
3. При получении ответа клиенту нужно записать токен, чтобы при следующих обращениях к серверу прикреплять токен к запросу, каждый раз подтверждая, что пользователь авторизован и может совершить нужное ему действие.
4. После записи токена клиент перенаправит пользователя на страницу `/admin/dashboard`, выполнив тем самым ещё один запрос к серверу. Он будет отличаться от привычных тебе, так как клиенту нужно получить HTML-страницу, а не какую-то информацию из базы данных.
5. При таком запросе серверу нужно будет как-то проверить авторизацию пользователя, чтобы вернуть на клиент страницу, которой ещё не существует.

В приложении Pindie мы уже работали с `JWT`-токеном и записывали его в локальное хранилище браузера — `localStorage`. Оно было доступно в любой момент времени и на любой странице, потому что Pindie — это SPA-приложение, то есть приложение с одной страницей. 

Как ты уже знаешь, перемещение между страницами в таком приложении происходит чисто визуально. На самом деле мы не покидаем текущую страницу, это JavaScript меняет контент внутри неё так, что кажется, будто мы переместились на другую страницу.

Но интерфейс нашей админки не SPA-приложение и при запросе страницы админки ты не сможешь обратиться к `localStorage`, потому что самой страницы у тебя ещё не существует.

## Куки — печеньки программистов

**Cookie,** они же куки, — это небольшие файлы с данными, которые передаются между клиентом и сервером при каждом запросе. Они позволяют серверам помнить информацию о пользователе, к примеру его `JWT`-токен, что особенно важно при работе в админке.

С этим механизмом и работает наш новый интерфейс админки. При авторизации, когда интерфейс получает ответ от сервера, он записывает `JWT`-токен пользователя в куки. Происходит это командой 👇🏻

```javascript
document.cookie = `jwt=${jwt}`;
```

В куки можно записать и несколько значений. Данные внутри будут похожи на набор переменных, разделённых между собой `;`. К примеру, вот так 👇🏻

```javascript
jwt=какой-то_токен;username=aski;email=aski@example.com
```

Получить данные, которые хранятся в куки, из браузера можно довольно легко. Достаточно обратиться к `document.cookie`, где они и хранятся 👇🏻

```javascript
const myCookies = document.cookie; // Запишет все куки в переменную myCookies
console.log(document.cookie) // Просто выведет все куки в консоль
```

С точки зрения безопасности важно использовать специальные атрибуты, такие как `HttpOnly` или `Secure`, чтобы защитить данные куки от злоумышленников. Также важно ограничивать время жизни куки, чтобы своевременно обновлять их данные для большей безопасности. 

Вот список самых важных атрибутов 👇🏻

- `domain` — адрес сайта, которому будут доступны куки.
- `path` — путь внутри сайта, по которому будут доступны куки.
- `secure` — защищает куки, запрещая передавать их по незащищённому протоколу HTTP, делает их доступными только при запросах через HTTPS.
- `max-age` — время жизни куки, задаётся в секундах.
- `expires` — точная дата и время, когда куки станут устаревшими.

Вот так могут выглядеть куки с указанными атрибутами 👇🏻

```javascript
jwt=token;domain=localhost:3001;path=/;secure;max-age=3600;
```

## Куки в действии

Для работы с куки на стороне сервера необходимо установить специальный пакет `cookie-parser`. Запусти команду установки в терминале проекта 👇🏻

```bash
npm install cookie-parser
```

Этот пакет служит миддлваром и играет важную роль в управлении куки. Он анализирует куки, отправляемые браузером в заголовках запроса, и делает их доступными в объекте `req.cookies`. Это позволяет легко извлекать и использовать куки в приложении.

Добавь этот миддлвар к остальным в файле `app.js` 👇🏻

```javascript
// Другие импорты
const cookieParser = require("cookie-parser");

// Конфигурация приложения

app.use(
  cors,
  cookieParser(), // Добавляем миддлвар для работы с куки
  bodyParser.json(),
  apiRouter,
  express.static(path.join(__dirname, "public"))
);

// Остальной код
```

Теперь займёмся обработкой запросов, которые отправляет клиент, чтобы получить нужную ему страницу. Наш `apiRouter` уже принимает и обрабатывает запросы от клиента, но он не подойдёт для обработки запросов на получение страниц, так как его основная задача — работа с данными.

Для этих типов запросов нужно создать отдельный роутер. В папке `routes` добавь новый файл `pages.js`. Этот самостоятельный роутер будет отвечать только за выдачу страниц, а не за работу с базой данных. Создай сам роутер 👇🏻

```javascript
// routes/pages.js
const pagesRouter = require("express").Router();
```

В нашем новом интерфейсе они следующие:

- `index.html` в корне папки `public` — страница с формой авторизации, отображаемая по умолчанию. Она должна быть доступна по маршруту `/`
- `dashboard.html`, расположенная по пути `public/admin`, — страница админки, на которой пользователь может управлять данными. Должна быть доступна по маршруту `/admin/dashboard`

Со страницами всё ясно: `index` — для авторизации, `dashboard` — для админов.

Теперь создай контроллер, который будет отдавать страницу для авторизации. Сейчас она уже отображается по умолчанию при переходе на `localhost:3000/`, но этого недостаточно. 

Контроллер должен проверять авторизацию пользователя, взаимодействуя с куки, переданными в запросе. Если пользователь уже авторизован, то его не надо пропускать на страницу авторизации — контроллер должен будет перенаправить его на страницу для админов, защищая приложение от возможности авторизоваться ещё раз, что может вызвать путаницу и привести к ошибкам.

Новый контроллер затрагивает процесс авторизации, поэтому создавать отдельный модуль не придётся. Добавь контроллер в файле `auth.js` папки `controllers` 👇🏻

```javascript
// Импорты и другие функции-контроллеры
const sendIndex = (req, res) => {}
```

Функция-контроллер `sendIndex` принимает параметрами объект запроса, из которого нужно будет достать куки, и объект ответа, в котором нужно вернуть запрашиваемую страницу. Первым шагом проверь: есть ли внутри объекта `req` куки с `JWT`-токеном 👇🏻

```javascript
const sendIndex = (req, res) => {
  if (req.cookies.jwt) {}
};
```

Если токен на месте, попробуй проверить его, используя метод `verify`, которым мы уже пользовались в уроке «Старый друг JWT» 👇🏻

```javascript
const sendIndex = (req, res) => {
  if (req.cookies.jwt) {
    try {
      jwt.verify(req.cookies.jwt, "some-secret-key");
    } catch (err) {
	   // Здесь будет обработка ошибки 
    }
  }
};
```

В случае если токен не устарел и принадлежит реальному пользователю, который уже авторизован, нельзя пускать его на страницу с формой для авторизации. Вместо этого нужно отправить в ответе страницу админки, где он сможет работать с данными. 

Сделать это можно ещё незнакомым тебе методом `sendFile`. Он позволяет легко отправить в ответе нужный файл, не прибегая к дополнительным проверкам. Всё, что тебе нужно, — указать путь до файла. Чтобы указать корректный и безопасный путь, воспользуйся встроенным в Node.js модулем `path` 👇🏻

```javascript
const sendIndex = (req, res) => {
  if (req.cookies.jwt) {
    try {
      jwt.verify(req.cookies.jwt, "some-secret-key");
      return res.sendFile(
        path.join(__dirname, "../public/admin/dashboard.html")
      );
    } catch (err) {
	   // Здесь будет обработка ошибки 
    }
  }
};
```

Обращаясь к объекту ответа, ты вызываешь метод `sendFile` и передаёшь в него путь до страницы админки. Сам путь собираешь по кусочкам, используя метод `join` модуля `path`. Он позволяет соединить два пути в один полный и безопасный. 

Так, в метод `join` ты сначала передаёшь `__dirname` — полный путь до твоего контроллера, то есть до файла `auth.js`, а затем путь до интересующего файла — HTML-страницы админки. Ориентируясь на указанный путь, метод `sendFile` берёт HTML-файл, который был указан, и отправляет его ответом на клиент.

Перед обращением к методу `sendFile` объекта `res` используй `return`, указывая функции, что после этого действия её нужно завершить и ничего дальше выполнять не следует.

Если при проверке токена возникнет ошибка, это будет говорить о том, что токен юзера уже устарел. Обрабатывать ошибку будет блок `catch`, а внутри него тебе нужно будет отправить в ответе пользователю страницу с формой авторизации 👇🏻

```javascript
const path = require("path");
// Импорты и другие функции-контроллеры

const sendIndex = (req, res) => {
  if (req.cookies.jwt) {
    try {
      jwt.verify(req.cookies.jwt, "some-secret-key");
      return res.sendFile(
        path.join(__dirname, "../public/admin/dashboard.html")
      );
    } catch (err) {
      res.sendFile(path.join(__dirname, "../public/index.html"));
    }
  }
};
```

Здесь ты прибегаешь к тому же методу `sendFile`, но вместо страницы админки отправляешь на клиент страницу с формой для авторизации.

Заключительным шагом сделай то же самое после блока `if`, чтобы, в случае отсутствия куки или `JWT`-токена внутри них, контроллер также отправлял на клиент страницу с формой авторизации 👇🏻

```javascript
const sendIndex = (req, res) => {
  if (req.cookies.jwt) {
    try {
      jwt.verify(req.cookies.jwt, "some-secret-key");
      return res.sendFile(
        path.join(__dirname, "../public/admin/dashboard.html")
      );
    } catch (err) {
      res.sendFile(path.join(__dirname, "../public/index.html"));
    }
  }
  res.sendFile(path.join(__dirname, "../public/index.html"));
};
```

Ещё раз проговорим, как он работает:

- Проверяет, есть ли куки и `JWT`-токен пользователя внутри них.
- Если у пользователя не заданы куки или в них нет токена, в ответе возвращается страница с формой авторизации.
- Если есть, в ответе отправляет клиенту страницу для админов.

Теперь можно вернуться к созданию маршрутов в новом роутере. Добавь в роутер обработку `GET`-запросов по маршруту `/` 👇🏻

```javascript
const pagesRouter = require("express").Router();
const { sendIndex } = require("../controllers/auth.js");

pagesRouter.get("/", sendIndex);
```

Этот маршрут — точка входа в приложение, и при переходе по адресу `localhost:3000/` серверу будет отправлен запрос на получение страницы с формой авторизации. Этот запрос обработает новый контроллер `sendIndex`

Отлично! Не забудь экспортировать роутер и добавить его в файле `app.js`, чтобы он использовался приложением 👇🏻

```javascript
// Импорты и конфигурация приложения

app.use(
  cors,
  cookieParser(),
  bodyParser.json(),
  pagesRouter, // Добавляем роутер для страниц
  apiRouter,
  express.static(path.join(__dirname, "public"))
);

// Остальной код
```

## Подобьём итоги

При заполнении данных в форме клиент отправляет запрос на сервер с просьбой авторизовать пользователя. Сервер проверяет информацию и в случае успешной авторизации отправляет на клиент уникальный `JWT`-токен и другие данные юзера. Клиент, получив ответ, записывает токен в куки для всех последующих запросов и отправляет серверу новый запрос с просьбой пустить его на страницу админки. Сервер при получении такого запроса считывает из куки токен пользователя и проверяет его ещё раз, после чего отправляет в ответе нужную страницу.

Обрати внимание на скринкаст. После авторизации интерфейс сам перенаправляет пользователя на `localhost:3000/admin/dashboard`. А запросы на этот маршрут твой сервер пока обрабатывать не умеет. 

Чтобы увидеть страницу админки, нужно вернуться обратно на `localhost:3000/`, где при переходе вновь сработает `sendIndex` и ты увидишь долгожданную страницу админки. При каждой перезагрузке этой страницы `sendIndex` будет вновь и вновь проверять куки и токен пользователя, не позволяя авторизованному юзеру увидеть страницу с формой.
