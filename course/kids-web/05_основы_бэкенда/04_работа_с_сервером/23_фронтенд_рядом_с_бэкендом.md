# Фронтенд рядом с бэкендом

Процесс запуска фронтенда на ВМ — задание не из лёгких, поэтому действовать сегодня будешь поэтапно:

1. Создашь домен для фронтенда — именно его будет вводить пользователь в адресную строку, чтобы открыть пользовательский сайт Pindie.
2. Используя `git`, загрузишь из удалённого репозитория на виртуальную машину код фронтенда.
3. Создашь Nginx-конфиг, который позволит сайту Pindie открываться по твоему домену.
4. Подключишь сертификат, чтобы сайт открывался по защищённому протоколу `https`
5. Соберёшь продакшн-версию фронтенда, то есть получишь итоговые `.js,.css,.html`-файлы, которые попадут пользователю в браузер.
6. Запустишь Next.js-сервер, который будет отправлять клиенту эти файлы.
7. Настроишь автозапуск Next.js-сервера с помощью менеджера PM2.

## Создаём домен

Тут всё просто: нужно повторить шаги, которые мы уже выполняли в уроке «Выпуск доменов», только работать будешь во вкладке `Фронтенд`

В качестве примера для нашего урока мы создали домен `pindie-frontend.nomoredomainswork.ru`, тебе же нужно будет придумать какой-нибудь другой, свой.

## Загружаем код на виртуальную машину

Для того чтобы всё запустилось без ошибок и проблем, перед тем, как загрузить код на виртуальную машину, тебе необходимо внести некоторые изменения в него для фронтенда и бэкенда.

На самом деле часть изменений уже должна быть внесена после урока «Запускаем Pindie: бэк отдельно, фронт отдельно». Сейчас просто убедись, что весь нужный код из урока добавлен и всё с ним ок.

### Правим фронтенд

Супер! Во фронтенде осталось только поменять значение переменной `BASE_URL` на твой домен бэкенда, который создали в уроке «Выпуск доменов». 

Для этого зайди в файл `/app/api/config.js` своего Next.js-приложения. Должно получиться так 👇🏻

```javascript
// Мы используем домен бэкенда, который создали для этого урока,
// а тебе нужно будет указать свой
export const BASE_URL = 'https://pindie-backend.nomoredomainswork.ru/api'
```

Теперь необходимо запушить все изменения в удалённый репозиторий, используя всего три команды. Во-первых, в корне своего фронтенд-проекта добавь команду 👇🏻

```bash
git add .
```

Затем создай коммит 👇🏻

```bash
git commit -m "<сообщение коммита>"
```

И отправь его в удалённый репозиторий 👇🏻

```bash
git push
```

Далее перейди на свою ВМ — как это сделать, мы показывали в уроке «Доступ к серверу по SSH» — и {{склонируй репозиторий}}[web_teens_theme4_lesson_11_«склонируй репозиторий»] со своим проектом.

### Правим бэкенд

Здесь тоже внеси всего лишь одно изменение. В файле `/middlewares/cors.js` в массив `allowedCors` добавь адрес фронтенда, с которого будут приходить запросы на твой бэкенд.

В нашем примере мы добавили `https://pindie-frontend.nomoredomainswork.ru` — не забудь поменять адрес на свой. А ещё в CORS нужно внести спецправила с разрешёнными типами запросов и заголовками. Вот как будет выглядеть итоговый файл `/middlewares/cors.js` 👇🏻

```javascript
// Вместо нашего адреса вставь свой
// Можно ещё не удалять адреса с localhost, но мы удалили для краткости
const allowedCors = ["https://pindie-frontend.nomoredomainswork.ru"];

function cors(req, res, next) {
  const { origin } = req.headers;

  if (allowedCors.includes(origin)) {
    res.header("Access-Control-Allow-Origin", origin);
  }
  res.header("Access-Control-Allow-Methods", "GET,HEAD,PUT,PATCH,POST,DELETE");
  res.header("Access-Control-Allow-Headers", "Access-Control-Allow-Headers, Origin,Accept, X-Requested-With, Content-Type, Access-Control-Request-Method, Access-Control-Request-Headers, Authorization");
  next();
}

module.exports = cors;
```

Так как на виртуальной машине уже есть папка с проектом бэкенда, тебе нужно перейти в неё и выполнить команду `git pull`. Таким образом ты загрузишь изменения в файле `/middlewares/cors.js` из удалённого репозитория на виртуальную машину.

## Настраиваем Nginx для фронтенда

Nginx тебе уже знаком по одноимённому уроку. Там мы настроили проект так, что к твоему бэкенду можно слать запросы не просто по IP виртуальной машины, но и по читаемому адресу. Для фронтенда тебе нужно сделать ровно то же самое, только конфиг мы предлагаем использовать уже готовый — `default`, так быстрее. Таким образом, у твоего сайта c играми тоже появится читаемый адрес, который пользователь сможет запомнить и вручную вводить в адресной строке. 

Для этого на виртуальной машине перейди в папку с конфигами Nginx 👇🏻

```bash
cd /etc/nginx/sites-available
```

Далее выполни команду для редактирования конфига по умолчанию 👇🏻

```bash
sudo nano default
```

Перед тобой откроется окно с множеством разных строк — это базовая конфигурация, которую тебе нужно полностью удалить. Для этого стрелкой вверх переведи курсор на самую первую строку и нажимай `CTRL + K` до тех пор, пока конфиг не опустеет.

После этого добавь следующее содержимое 👇🏻

```bash
server {
      listen 80;

      server_name <твой_домен_фронтенда>;

      location / {
                proxy_pass http://localhost:3000;
                proxy_http_version 1.1;
                proxy_set_header Upgrade $http_upgrade;
                proxy_set_header Connection 'upgrade';
                proxy_set_header Host $host;
                proxy_cache_bypass $http_upgrade;
      }
}
```

Эта конфигурация очень похожа на ту, что мы добавляли для бэкенда.

## Подключаем сертификат

Мы уже подключали SSL-сертификат для адреса бэкенда в уроке «HTTPS». Сейчас нужно сделать почти то же самое — отличие лишь в том, что в вопросах после команды `sudo certbot --nginx`, где спрашивают, для какого домена нужно подключить сертификат, нужно выбрать домен для фронтенда. 

Для этого введи, когда попросят, номер соответствующего домена и нажми кнопку `Enter` 👇🏻

## Запуск Next.js-сервера с помощью PM2

- Перейти в папку с фронтенд-проектом 👇🏻

```bash
cd <путь_к_папке_которую_склонировали_из_github>
```

- Выполнить команду сборки 👇🏻

```bash
npm run build
```

Запустить Next.js-сервер можно командой `npm start`, но в этом случае процесс может завершиться в любой момент и больше автоматически не запустится. Поэтому лучше запусти сервер командой `pm2 start npm -- start`. Таким образом `pm2` будет поддерживать процесс сервера всегда в рабочем состоянии.

После запуска команды PM2 может сказать в ответ, что конфигурация теперь обновлена и отличается от той, что используется во время перезапуска. Предложит тебе ввести команду `pm2 save`, сделай это.

## Архитектура приложения

Вот что сейчас запущено на твоей виртуальной машине 👇🏻

![](https://pictures.s3.yandex.net/resources/24_1715853506.jpg)

- Веб-сервер Nginx c двумя конфигурациями для фронтенда и бэкенда
- Node.js-сервер — код бэкенда
- Next.js-сервер — код фронтенда

В данном случае веб-сервер Nginx выступает окном во внешний мир, а это значит, что адреса `https://pindie-backend.nomoredomainswork.ru` и `https://pindie-frontend.nomoredomainswork.ru` (у тебя они другие) доступны из интернета. Когда браузер делает запрос по ним, первым его встречает Nginx и, в зависимости от адреса, перенаправляет в нужное приложение, которое запущено на `localhost`

В реальной жизни так делают только для сайтов с совсем небольшим количеством пользователей. Чаще и Nginx, и Next.js-сервер, и Node.js-сервер запущены на разных ВМ, да ещё и не в одном экземпляре. Но это уже вопросы балансировки нагрузки на разные части всего приложения — именно это и называют архитектурой.
